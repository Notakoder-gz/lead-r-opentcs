# История создания и архитектура проекта (Lead-R OpenTCS & Open-RMF)

Привет! Если ты читаешь этот документ, значит, тебе предстоит работать с этой инфраструктурой, либо ты хочешь понять, как и почему мы объединили OpenTCS и Open-RMF в единый оркестратор флота роботов.

Этот проект начался с амбициозной идеи: взять мощный маршрутизатор (OpenTCS) и современную систему управления флотами (Open-RMF), подружить их друг с другом и заставить работать с реальными роботами (на базе микроконтроллеров ESP32 / micro-ROS). По пути мы набили много шишек, и этот документ — выжимка нашего опыта.

## 1. Особенности проекта и почему всё сделано именно так

Мы работаем в парадигме **Monorepo**. Это значит, что весь код кастомных адаптеров, все конфигурации и `docker-compose.yml` лежат в одном месте. Мы деплоим это на сервер через **Portainer** (или обычный Docker Compose).

### А. Битва за сеть: ESP32 против ROS 2
Самая большая проблема, с которой мы столкнулись — **Wi-Fi шторм**.
По умолчанию ROS 2 использует протокол FastDDS, который рассылает широковещательные (multicast) UDP-пакеты для поиска других узлов. Когда запускается тяжелый стек Open-RMF, сеть мгновенно забивается этим мусором. Мощные компьютеры этого не замечают, но наши реальные роботы с ESP32 просто захлебывались и падали из-за переполнения буфера.

**Как мы это решили:**
Мы создали кастомный файл `fastdds_profiles.xml`. Он жестко ограничивает размеры пакетов и буферов.
Мы пробрасываем этот файл во **все** ROS 2 контейнеры (`rmf_schedule`, `building_map_server`, `fleet_adapter` и даже `rmf_api_server` — для него пришлось написать отдельный `Dockerfile`, чтобы "впечь" XML прямо в образ, так как Portainer иногда криво маунтит одиночные файлы).
Переменная `FASTDDS_DEFAULT_PROFILES_FILE=/fastdds_profiles.xml` заставляет ROS 2 "успокоиться", и роботы перестают отваливаться.

### Б. Фокус с OpenTCS и пустыми папками
Ядро OpenTCS оказалось капризным. Когда Docker монтирует пустую папку с сервера (например, `/home/amy/.../config`) поверх внутренней папки `/opt/opentcs/config`, он затирает дефолтные конфигурации, и ядро уходит в бесконечный цикл перезагрузок.
**Решение:** В `Dockerfile` для OpenTCS мы добавили `entrypoint.sh`. При старте он проверяет: если примонтированная папка пуста, он бережно копирует туда дефолтные файлы из бэкапа, и только потом запускает ядро. Это делает развертывание на новых серверах абсолютно безболезненным.

### В. Питон, ROS 2 и зависшие потоки
В нашем адаптере `yahboom_adapter.py` мы используем библиотеку `rmf_adapter` (C++ биндинги для Python). Изначально мы пытались использовать стандартный `rclpy.spin()`, но скрипт падал с ошибкой `AttributeError: 'rmf_adapter.Node' object has no attribute 'executor'`.
Разгадка проста: C++ ядро адаптера само крутит потоки в фоне (`adapter.start()`). Нам нужно было просто не дать питоновскому скрипту закрыться. Поэтому вместо `spin()` мы используем простой `while rclpy.ok(): time.sleep(1)`.

### Г. Дашборд без паролей
В Open-RMF довольно сложная система авторизации (обычно нужен Keycloak). Чтобы упростить разработку и тестирование, мы перевели `REACT_APP_AUTH_PROVIDER` в режим `stub` и убрали лишние переменные. Теперь дашборд пускает без лишних вопросов.

## 2. Зачем нам `.env` и почему там такие пути?

Поскольку мы разворачиваем систему через Portainer, мы не можем полагаться на относительные пути (`./`) для маунта `volumes`. Если Portainer запустит стек из своей внутренней временной папки, он создаст пустые директории вместо того, чтобы подтянуть наши реальные файлы (карты, конфиги), лежащие на сервере.

Поэтому мы вынесли **все** пути и IP-адреса в `.env` файл.
Вот что значит каждая переменная (на примере нашего дефолтного сервера `192.168.3.142` пользователя `amy`):

* `HOST_IP=192.168.3.142` — IP-адрес сервера. Он нужен ядру OpenTCS (для RMI) и Дашборду RMF (чтобы знать, куда стучаться в API).
* `ROS_DOMAIN_ID=20` — Изолирует нашу ROS 2 сеть от других роботов в здании. Все контейнеры должны использовать один ID.
* `FASTDDS_PROFILE_FILE=/home/amy/lead-r-opentcs/fastdds_profiles.xml` — Абсолютный путь к спасителю наших ESP32.
* `OPENTCS_CONFIG_DIR`, `RMF_MAPS_DIR` и др. — Жестко заданные пути на сервере. Docker Compose возьмет файлы именно оттуда, гарантируя, что мы не потеряем данные при пересоздании контейнеров.

## 3. Как с этим работать (Инструкция по деплою)

Если ты хочешь развернуть этот проект на новом сервере или обновить текущий:

1. **Склонируй репозиторий:**
   ```bash
   git clone <url-репозитория> /home/amy/lead-r-opentcs
   cd /home/amy/lead-r-opentcs
   ```

2. **Настрой окружение:**
   Скопируй шаблонный файл:
   ```bash
   cp .env.example .env
   ```
   Открой `.env` в редакторе (например, `nano .env`) и убедись, что `HOST_IP` совпадает с IP-адресом твоего сервера, а абсолютные пути ведут туда, куда нужно.

3. **Подготовь папки (если сервер чистый):**
   Убедись, что пути, указанные в `.env` (например, `/home/amy/deploy_maps`), существуют. Если нет — создай их.

4. **Запуск через Portainer (или локально):**
   В Portainer ты можешь создать "Stack", подключив этот Git-репозиторий. Укажи путь к `docker-compose.yml`.
   *Важно:* Portainer сам подтянет код, соберет кастомные образы адаптеров (благодаря тегам `build: ./adapters/...`) и запустит их.

   Либо, если запускаешь руками через терминал:
   ```bash
   docker compose up -d --build
   ```

5. **Первые шаги:**
   - Открой клиент OpenTCS, создай карту и поставь виртуальных роботов (`yahboom_01`, `yahboom_02`) на стартовые точки.
   - Пока ты не поставишь их на точки, адаптер будет писать в логи: `⚠️ yahboom_01 не на точке и не имеет точных координат`. Как только робот появится в OpenTCS, он тут же отобразится в Open-RMF!
