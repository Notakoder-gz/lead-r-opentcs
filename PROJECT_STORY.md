# История и архитектура проекта: OpenTCS Deployment Stack

Привет! Этот документ описывает процесс создания и логику работы данного репозитория. Я решил собрать этот проект, чтобы упростить развертывание системы управления роботами на базе **OpenTCS**.

Ранее я пытался использовать сложную связку Open-RMF + OpenTCS + самописные мосты, но понял, что сращивать такие огромные системы очень тяжело. Поэтому я решил пойти от малого к большому: сначала сделать стабильно работающий флот на чистом OpenTCS, научиться подключать к нему физических роботов, а уже потом думать о более высоких уровнях абстракции.

Этот репозиторий (в текущей ветке `opentcs-only`) — это мой "чистый" старт.

---

## 🏗 Как устроен проект

Архитектура проекта была значительно упрощена. Вместо сборки из исходников с помощью Gradle, я использую подход контейнеризации готовых официальных релизов. Это позволяет развернуть серверную часть за пару минут на любом ПК или сервере.

В `docker-compose.yml` сейчас крутятся два основных сервиса:

1. **`opentcs_kernel`**:
   - Это мозг системы. Он работает без графического интерфейса (headless) и отвечает за маршрутизацию и выдачу задач.
   - В Dockerfile происходит автоматическое скачивание официального бинарника `opentcs-7.2.1-bin.zip` с GitHub, его распаковка и подготовка.
   - Специальный скрипт `entrypoint.sh` следит за тем, чтобы при первом запуске в пустые примонтированные папки скопировались дефолтные конфиги, иначе ядро упадет с ошибкой.

2. **`opentcs_web`**:
   - Так как официальные клиенты OpenTCS (Plant Overview и Operations Desk) — это тяжелые десктопные Java-приложения, мне нужен был способ быстро мониторить флот через телефон или браузер.
   - Я написал простейший веб-дашборд на Node.js. Он стучится в Web API ядра (порт 55200) и отображает в реальном времени статус машинок и заказов.

*Примечание: Изначально я пробовал поднять VNC-сервер в браузере, чтобы запускать Java-клиенты прямо там, но оказалось, что это излишне. Гораздо удобнее запускать Plant Overview на своем основном рабочем ПК с Windows и просто подключаться к ядру на сервере по сети.*

## ⚙️ Настройка переменных окружения (`.env`)

Для деплоя через Portainer или консоль Docker нужно обязательно настроить файл `.env`. Вот почему здесь прописаны именно такие переменные (значения взяты из моего текущего сетапа):

- **`HOST_IP=192.168.3.142`**
  - **Зачем:** Это статический IP моего сервера в локальной сети.
  - **Важно для OpenTCS:** Java RMI (Remote Method Invocation), через который десктопный клиент общается с ядром, очень капризен к сетям Docker. Если не передать ядру реальный IP хоста (`-Djava.rmi.server.hostname=${HOST_IP}`), то клиент на Windows просто не сможет подключиться к ядру в Docker-контейнере.
  - **Важно для Web:** Дашборд использует этот IP, чтобы знать, куда отправлять REST API запросы.

- **`OPENTCS_CONFIG_DIR=/home/amy/fleet_server/opentcs/config`**
- **`OPENTCS_DATA_DIR=/home/amy/fleet_server/opentcs/data`**
  - **Зачем:** Я использую абсолютные пути хостовой машины вместо относительных (`./config`).
  - **Почему:** При деплое стеков через Portainer, Docker Compose часто создает временные директории для сборки, и относительные пути мапятся неправильно, что приводит к созданию пустых папок или ошибкам прав доступа. Абсолютный путь гарантирует, что конфиги и модель склада всегда лежат в конкретной папке на сервере у пользователя `amy`.

## 🚀 Как с этим работать

1. **Развертывание на сервере:**
   Зайдите на сервер (192.168.3.142), скопируйте `.env.example` в `.env`, проверьте пути. Затем запустите:
   ```bash
   docker compose up -d --build
   ```

2. **Редактирование карты (Plant Overview):**
   - Я не запускаю редактор карты на сервере. Я скачиваю OpenTCS v7.2.1 на свой личный компьютер (Windows).
   - Запускаю `startPlantOverview.bat`.
   - В интерфейсе выбираю "Connect to Kernel", ввожу IP сервера `192.168.3.142` и порт `1099`.
   - Рисую карту, расставляю точки и сохраняю модель в ядро.

3. **Мониторинг:**
   - Просто открываю в браузере `http://192.168.3.142:3000` и вижу, что происходит с флотом.
